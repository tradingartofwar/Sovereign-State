# 低负担入门设计

## 用途

本文件与 GPT 入门设计配套，确保最需要人与 AI 协作支持的人，不会被技术设置排除在外。疾病、残障、年龄、认知负担、孤立、经济困难、疲惫或同时应对多个机构，可能使一个人尤其需要连续性、倡导、组织、记忆、解释和办事支持，却最没有精力配置账号、认证或工具。

必须区分“现在获得帮助”和“以后建立持久基础设施”。

> 任何基础设施要求，都不应阻止一个人立即获得认知支持。

只在有助于保存、扩展或保护帮助时，逐步引入基础设施。

## 1. 核心问题

常规技术入门往往假设本人能管理账号、密码和多因素认证，创建或复制 Git 仓库，理解公私区别，连接 GPT，管理权限，识别安全风险，恢复登录，并区分操作系统与存储工具。

这些对熟练者可能很简单，对生病、残障或不堪重负的人却可能成为不可逾越的门槛。最需要支持的人，反而最难完成支持系统的设置。

这是架构问题，不是使用者的失败。

## 2. 先帮助，再建设

初次体验应从“现在发生了什么？你希望我帮你承载什么？”开始，而不是要求先完成技术设置。

顺序是：

1. 立即提供帮助。
2. 建立有用的连续性。
3. 建立持久、由本人掌握的状态。
4. 按需采用高级设施。

GitHub、仓库、Codex、仪表盘和连接器是实现手段，不是获得帮助的入场券。

## 3. 阶段 0：立即开始

最低要求是能使用 GPT。本人可以用普通语言描述困难，例如看不懂拒绝信、记不住各机构的回复、文件分散或经常错过期限。

GPT 可以立即帮助梳理情况、区分紧急程度、整理文件与通信、建立时间线、发现缺失信息、准备问题、解释信件、记录期限、辨认已尝试的办法、寻找支持或升级处理路径，并在当前环境保存简洁摘要。

这个阶段不要求 GitHub 账号、仓库或开发环境。

## 4. 阶段 1：有用的连续性

当帮助有用后，让本人下次无需从头重建全部情况。使用当前环境能支持的最轻方式：持续对话或项目、个案摘要、当前状态文件、时间线、活跃问题、等待条件、重要期限、来源引用及少量下一步。

目标是明天能继续，不是立即建成完整系统。只询问保持连续性实际需要的信息。

## 5. 阶段 2：持久的私人状态

有了值得保留的内容后，可建议建立私人、持久、由本人所有的状态层。用用途解释：

> 现在已有不该丢失的信息、决定、期限和历史。我们可以建立一个你拥有的私人位置，让 GPT 可靠地回来继续。

设置应尽量简短并逐步引导：

1. 创建或登录账号。
2. 建立适当的安全认证。
3. 从模板创建私人仓库，或使用已存在且确认合适的私人仓库。
4. 给 GPT 适当权限。
5. 核验启动说明和当前状态可读取；在声称可维护状态前，另行核验无害写入。

本人无需理解 Git 内部机制。具体访问核验以入门说明为准。

## 6. 阶段 3：高级设施可选

VS Code、Codex、命令行、本地仓库、自动提交、仪表盘、连接器、专门代理、跨系统编排、共享关系空间和可编程流程，都应在真实用途支持时再引入。

一个永不学习 Git、永不开终端的人，也应能持续受益。设施服务于本人，不应成为本人必须服侍的新系统。

## 7. 有帮助者的入门

帮助者可能是亲友、照护者、社工、邻居、倡导者、个案经理、临床人员或志愿者。区分三个角色：

- **本人**：被支持的生活、状态与决定属于此人；其在能行使的范围内保有最终决定权。
- **GPT 伙伴**：在授权边界内承担结构、连续性、综合、检索、比较、解释和技术执行。
- **可信设置帮助者**：临时或持续协助设置、收集文件、交通、沟通等实际事务。

协助能力不自动赋予支配本人状态的权力。技术访问不等于决定什么重要；持有密码不等于拥有此人的系统；创建仓库不等于拥有治理权。

## 8. 安全认证不应成为障碍

使用与实际设备、账号和风险相适应、负担尽量小的安全方式。可能包括设备通行密钥、平台认证、可信登录服务、适当的认证应用，以及明确授权的帮助者协助。

不要把某一种认证技术固定为架构要求。技术会变，原则不变：保护应充分，负担应适当。

设置时就建立恢复路径。丢失一部手机就永久失去访问的系统，没有实现可访问性目标。

## 9. 逐步展示复杂性

新使用者不必先学会权威状态、展示层、来源追溯、委托权限、分支、提交或代理架构等词汇。

GPT 可以按照这些概念工作，只解释有助于本人作出有意义决定的部分。

## 10. 根据可用精力调整

只能投入十分钟，就给十分钟内可做的下一步。疼痛时不要一次问二十个问题。打字困难时支持语音。长信件先给简明解释，再按需展开。可信帮助者可在授权内分担事务。

不要因为 AI 能生成庞大计划，就把庞大计划交给已经不堪重负的人。人的可用精力是实际工作约束。

## 11. 以具体个案提供支持

起初可能更需要个案伙伴，而不是生活仪表盘。可保留：

- 当前情况：正在发生什么？
- 紧急风险：食物、住所、药物、出行、安全、水电或健康恶化等。
- 涉及机构：哪些部门、保险方、雇主、医院、法院或支持组织？
- 既往行动：已经尝试什么？
- 证据：有哪些信件、决定、申请、日期或通话记录？敏感原件保留在合适的受保护来源。
- 阻碍：流程卡在哪里？
- 期限：哪些日期重要？
- 等待条件：谁应回复？下一步依赖什么？
- 下一步：现在最小而有用的行动是什么？

这能立即产生价值，也自然形成持久状态的起点。

## 12. 不要重建官僚负担

避免不必要的表格、分类、必填字段、问卷、重复输入、新账号、术语、没有实际意义的重复确认，以及仅因模板存在就创建的架构。

尽量通过普通对话获得信息。结构主要由 AI 承担。本人决定什么重要以及委托哪些判断，不必独自发现或记住所有意义和状态。AI 可在委托内发现、解释、保存和呈现什么重要。

## 13. 公共入门入口

公共说明应无需拥有 GitHub 账号即可阅读。本人可以只给 GPT 一个公开入口并说：

> 阅读这些说明，帮我开始。

公共仓库提供工作原则，不应成为必须先配置好的技术环境。

## 14. 可访问性验收

用缺乏技术经验、压力大、身体受限或慢性病、不了解 GitHub 与 AI 系统、可能依赖帮助者的真实使用情境检验。系统应能：

1. 立即帮助。
2. 理解当前问题。
3. 避免使人不堪重负。
4. 保存足够状态以便继续。
5. 区分本人和设置帮助者。
6. 只在有用时引入持久存储。
7. 无需技术专长即可完成引导式账号与安全设置。
8. 中断后连贯恢复。
9. 保留本人的决定权。
10. 减少认知负担。

如果必须先成为技术熟手才能受益，入门设计就失败了。

## 15. 与整体设计的关系

这是整体 GPT 入门中的可访问性视角与实施路径，不是另一个操作系统。

即使本人可用的技术、认知、身体、经济或情绪资源很少，系统也应有用。减少无谓阻力的经验应进入默认设计，因为它帮助所有人。

## 16. 核心表达

> **先帮助，再连续性，再基础设施。复杂性必须有实际理由。**

最需要认知伙伴的人，不应因为无法配置背后的机器而被排除。机器应逐渐退到关系背后。
