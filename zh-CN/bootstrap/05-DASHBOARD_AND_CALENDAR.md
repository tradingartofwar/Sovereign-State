# 可选第 5 步——有用时再增加看板或日历

看板和日历是两项独立、可选的显示能力。没有它们，个人记录仍然可以完整有用。若 state/CURRENT_STATE.md 已经清楚够用，可继续只用它，不建立漂亮却空洞的界面。

建立或大幅修改看板前，读 [看板完整性](../doctrine/DASHBOARD_INTEGRITY.md)。

## 何时值得提出看板

应已满足：

- 本人私有仓库存在，直接读写都已验证；
- 决定权和隐私边界明确；
- 至少有一件真实、持续变化的事项；
- 每件事项都有当前情况、下一步或再次关注条件、负责人及来源边界；
- 至少一次后续更新或纠正已成功处理；
- 视觉界面有望在本人的实际设备上减轻负担；
- 看板的权威来源已明确；
- 活跃事项都能显示，或有明确的排除理由。

不从文件数量、事项数量或兴奋程度推断准备程度。

## 如何提出

> 现在已有一些持续更新的信息。一个小看板可能帮助你看清什么重要、什么可以安心等待。没有看板，私有记录也能继续用。你觉得看板会有帮助吗？

本人接受后再建立。已有明确授权就不重复询问同一许可。

## 第一个看板

小而易读，只包含有真实内容支撑的部分：

- 优先事项／现在什么重要；
- 即将到来；
- 进行中的事项；
- 可以安心等待的事项；
- 项目、关系、兴趣或可能性；
- 最近变化；
- 来源及真实的“截至何时”；
- 如何报告变化或纠正。

选中的优先事项应说明为什么现在重要、下一步、时间或不确定性及复查日期。引用同一份事项记录，不另存一套任务。本人可用普通语言调整顺序。关系、兴趣或长期可能性即使没有截止日，也可能重要。重要性排序不等于严格执行顺序。其他已经到期的查看事项仍要可见，不把所有未完成工作都列成优先事项。

接受看板后，保留其地址、领域名称和基本布局；大改先提出，不悄悄替换。

## 从来源到显示的检查

每次更新：

1. 更新权威私有状态。
2. 从该状态更新看板。
3. 检查每件活跃事项是否显示或明确排除。
4. 区分报告、推断、过时和待核实信息。
5. 只有完成得到确认才移出当前关注，同时保留有意义的历史。
6. 验证纠正在接受的看板中实际出现。

只手动改看板不等于保存了可靠状态。显示故障不应危及源记录。

## 何时值得使用日历

至少有一项真实时间关系，且日历能帮助本人适时再关注，才提出日历。不要把每个日期都变成预约。

| 类型 | 含义 |
| --- | --- |
| 预约 | 固定外部安排 |
| 截止日期 | 必须在某日之前完成 |
| 计划行动 | 本人打算在某时行动 |
| 复查日期 | 到时检查最新状态 |
| 日常安排 | 重复活动 |
| 可能日期 | 暂定或未确认日期 |
| 可用时间 | 本人选择使用或分享的一段时间 |

同一事项可有准备复查、截止日和预约等多个再次关注点。各自保留标识、含义、日期或条件、负责人，以及待处理／已满足／已取消的状态。复查日期过去，只表示需要检查现状，不证明失败或完成。

每次关注都写明实际机制：在调度服务中已验证的提醒、外部日历事件、指定人工查看、有意安静等待，或尚未安排。适用时记录服务引用及上次设置检查。仓库或看板里的日期不等于已安排通知；日历事件也不证明提醒已开启或已经送达。没有实际支持且获授权的机制，不声称后台正在监控事件。

日期或状态变化时，在授权范围内修正源记录及受影响的实际提醒或日历，再验证显示。只改文字不会改动外部提醒。保留已满足或取消的关注点及原因。没有通知能力时说明限制，商定可用的人工查看方式。

初始日历可以从私有仓库生成；实际日历服务可之后另行授权连接。

## 接入日历服务后

- 实际日程由日历服务拥有。
- 事项、截止日和再次关注路径由私有状态来源拥有。
- 看板将二者结合成可纠正的显示。
- 连接日历不授权向他人或智能体分享。

对外分享遵循 [关系边界](../doctrine/RELATIONSHIP_BOUNDARIES.md)，只分享本人批准的限定内容。
