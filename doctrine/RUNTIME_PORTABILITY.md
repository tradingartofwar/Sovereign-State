# Runtime Portability

A sovereign human–AI operating state should survive the loss or replacement of a device, conversation, GPT runtime, dashboard, or technical helper.

## Distinct components

Keep these components distinguishable:

- the person and their authority;
- the GPT or other model;
- the instructions, tools, permissions, and workflows around the model;
- the private person-owned state repository;
- dashboards, calendars, and other projections;
- relationship channels;
- protected source systems.

The private repository is durable state machinery. It is not the person, the complete human–AI relationship, or the sovereign agent by itself.

## Replaceable surfaces

A laptop, phone, browser, ChatGPT thread, GPT version, connector, dashboard, or development environment may become unavailable. No single one should be the only route back to the person's current state.

The private repository should include a plain-language `RESUME_HERE.md` that states:

- what the repository is;
- the current bootstrap stage;
- the last established result;
- the next smallest step;
- any blocker;
- how a fresh GPT should re-enter;
- the current role of any trusted helper.

Do not place secrets or sensitive source material in the resume file.

## Interruption behavior

Before an interruptible setup or migration step:

1. update the private repository's bootstrap state;
2. update the human-readable resume point;
3. name the next smallest action;
4. preserve the blocker or return condition;
5. verify that another supported device or fresh GPT can understand where to resume when practical.

A new runtime should read current state before restarting onboarding or inventing a replacement architecture.

## Capability discovery

Product names, menus, plugins, connectors, and interfaces change. Inspect the capabilities available in the person's current environment. Explain what is actually available and use the least burdensome supported route.

Do not invent a capability, require a developer tool, or make one provider part of the constitutional meaning of the system.

## Portability standard

Portability is adequate when the person can:

- identify where durable state lives;
- reach or reconnect to it through a supported route;
- ask a fresh GPT to resume from current state;
- understand and correct the resulting orientation;
- continue without the original setup helper operating the system for them.

On re-entry, recover the live question, meaningful corrections, and authorized interaction preferences when available. Check fit through actual interaction. Access to the same records does not establish equivalent model behavior, learning, or understanding.

Provider substitutability, export, backup, and additional recovery mechanisms may be added when real risk or use warrants them. Do not promise portability that has not been tested.
